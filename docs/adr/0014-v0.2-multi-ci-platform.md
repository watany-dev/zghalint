# 0014. v0.2 — GitHub Actions 以外の CI 設定への対応

- Status: Proposed
- Date: 2026-09-08
- Related: `docs/design/v0.2-multi-ci-roadmap.md`（マイルストーンとルール案）、#262 / #270（bench 運用）、#281（`needs:` の循環検出）

## Context

zghalint は現在 GitHub Actions 専用のリンターである。YAML 層・診断型・出力・
設定・autofix エンジンは CI に依存しないが、`src/workflow/`（IR とパーサ）、
`src/rules/`（98 ルール）、`src/main.zig` のファイル発見は GitHub Actions の
スキーマと `.github/` の配置を前提にしている。

v0.2 では他の CI 設定も検査対象にしたい。動機は 3 つある。

1. GitHub 以外のホスティング（GitLab、Gitea / Forgejo、Bitbucket）にはオフラインで
   動く「セキュリティ寄り」のリンターがほとんどない。actionlint / zizmor 相当の
   ツールが存在しない領域で、zghalint の unique-win を作れる
2. GitHub と GitLab の両方に CI 設定を持つミラー運用のリポジトリは珍しくなく、
   1 バイナリで両方を見られることに価値がある
3. 「GitHub Actions 互換」を掲げる Gitea / Forgejo Actions は、既存のルールを
   ほぼそのまま適用できるにもかかわらず、現状は `gitea.*` コンテキストが
   EXPR002（unknown context）の偽陽性になるなど、方言差で使い物にならない

一方で制約もある。ゼロ依存・自前 YAML パーサという方針は維持する。既存ルールの
精度を落とす共通化はしない。CLI 契約（フラグ、終了コード、出力形状）は v0.1 で
固めた形を壊さない。

## Decisions

### D1. プラットフォームはファイル単位で決め、既定はパス規約から推定する

`Platform` enum（`github` / `gitea` / `forgejo` / `gitlab`、以後の追加はここに並ぶ）を
`src/platform.zig` に置き、`detectPlatform(path)` がパス規約から決める。

| パス | Platform |
| --- | --- |
| `.github/workflows/*.yml` / `action.yml` / `.github/dependabot.yml` | `github` |
| `.gitea/workflows/*.yml` | `gitea` |
| `.forgejo/workflows/*.yml` | `forgejo` |
| `.gitlab-ci.yml`、`*.gitlab-ci.yml` | `gitlab` |

パスだけでは決まらない場合がある。Gitea は `.gitea/workflows/` に加えて
`.github/workflows/` も読み、Forgejo は `.forgejo/` / `.gitea/` / `.github/` の
3 つを読む。Gitea にホストされたリポジトリが `.github/workflows/ci.yml` に
`gitea.*` を書くと、パス推定では `github` になり EXPR002 の偽陽性が残る。
このために `--platform <name>` と、設定ファイルの `platform:`（リポジトリ全体の
既定値。ホスティング先が Gitea / Forgejo ならこれを 1 行書く）を用意する。
既定のファイル発見（引数なし実行）は上表をすべて拾うので、GitHub にミラーされた
`.gitlab-ci.yml` も 1 回の実行で検査される。

1 回の実行で複数プラットフォームが混ざることを前提に設計する。プロセス単位の
モード切替（`zghalint gitlab ...` のようなサブコマンド）は採らない。ミラー運用の
リポジトリで 2 回実行させるのは、1 バイナリで済ませる動機と矛盾する。

### D2. IR はプラットフォームごとに分け、共通 IR を作らない

GitLab CI のジョブモデル（`stages` / `script` 配列 / `rules` / `include` / `extends` /
`default:`）は GitHub Actions の `Workflow → Job → Step` に写像できない。無理に
共通 IR に載せると、両方の最小公倍数しか表せず、`permissions` や `needs.<job>.outputs`
のような GitHub 固有のフィールドに依存する既存ルールが型を失う。

したがって:

- `src/workflow/` は GitHub Actions の IR のまま残す。ディレクトリ名の付け替え
  （`src/github/` 化）は差分が大きく、v0.2 の機能変更と混ぜない。必要なら v0.2 完了後の
  tidying として別途扱う
- GitLab は `src/gitlab/{types,parser,schema}.zig` に独立した IR とパーサを持つ
- ルールも `src/rules/gitlab/` に独立して置く。GitHub 側のルール関数を GitLab の型で
  呼ぶことはしない

共有するのは「テキストの性質」を見る部品だけである（D5）。「ジョブに timeout が
無い」のような構造ルールは、同じ趣旨でもプラットフォームごとに書き直す。

### D3. Gitea / Forgejo は GitHub Actions IR の方言として扱う

構文は同一なので、`Workflow` に `platform: Platform` を持たせ、方言差を知っている
ルールだけがそれを参照する。既知の差分はロードマップ §4.1 に列挙する。原則は
「方言で意味が変わるものは黙る、変わらないものはそのまま出す」。RUNNER002 /
RUNNER003 の「知らないものは黙る」（ADR 0011 / 0013）と同じ立場である。

Gitea / Forgejo 専用の新ルール ID は v0.2 では作らない。方言対応の価値は
「既存のルールが偽陽性なしに使えること」にある。

### D4. ルール ID はプラットフォーム接頭辞を付け、GitHub Actions の既存 ID は変えない

新しいプラットフォームのルールは `<PF>-<CAT><NNN>`（例: `GL-SEC001`）とする。
v0.2 の接頭辞は `GL`（GitLab）のみ。GitHub Actions の ID（`SEC001` 等）には
接頭辞を付けない。

検討した代替:

- **同じ ID を全プラットフォームで再利用する**（`SEC002` = script injection をどこでも）:
  設定の可搬性は高いが、`docs/rules.md` に書かれた SEC002 の意味
  （汚染源 `github.event.*`、`${{ }}` のテンプレート展開）は GitHub 固有で、
  GitLab では発火条件も severity も違う（ロードマップ §3 の注入モデル）。1 つの ID に
  2 つの意味を持たせると SARIF の rule descriptor と `docs/rules.md` が曖昧になる
- **GitHub Actions にも `GH-` を付けて揃える**: 既存の `.zghalint.yml` と SARIF の
  baseline を一斉に壊す。1.0 前とはいえ、得るものが見た目の対称性だけなので採らない

接頭辞付き ID を通すために、`docs_sync_test.zig` の `ruleRowId` を `[A-Z]+-`
接頭辞込みで読めるよう広げる（`config.zig` の `rules:` はキーをそのまま
`StringHashMap` に入れるので変更不要）。`registry.documented_rule_ids` は
全プラットフォームの ID の和集合になる。

### D5. 共有部品は先に `src/common/` へ切り出す（Tidy First）

GitLab のルールを書く前に、GitHub 側のルールに埋まっている汎用ロジックを
`src/common/` に移す。それぞれ挙動を変えない別コミットで行い、bench の
`--json` 出力が移動前後で一致することを完了条件にする。

| 部品 | 現在の場所 | 使う側 |
| --- | --- | --- |
| Docker イメージ参照の解析（タグ / digest / `latest`） | `security.zig` `isImagePinned`（SC001） | GL-SEC004 |
| 秘密情報リテラルの検出 | `security.zig` `checkStringForSecrets` | GL-SEC002 |
| シェル片のパターン走査（`curl \| sh`、変数参照） | `security.zig` `containsCurlWgetPipeShell` / `referencesShellVar`、`best_practices.zig` BP007 | GL-SEC001 / GL-SEC005 |
| lockfile 検出 | `workspace.zig` | GL-PERF001 |

`engine.Rule` からメタ情報（`id` / `name` / `description` / `severity` / `category`）を
`RuleMeta` として分離し、SARIF の rule descriptor と `docs/rules.md` の同期テストは
`[]const RuleMeta` を受け取る。フック（`check_workflow` 等）はプラットフォームごとの
`Rule` 型に残す。

### D6. ネットワークルールは v0.2 では GitHub のみ

`prefetch.zig` 以下の GitHub API 連携（SC003–SC006、SC008）はそのまま GitHub 専用と
する。GitLab の `include: project:` / `component:` の解決には GitLab API（self-hosted
ならホストごと）が要り、Docker Hub の tag → digest 解決は両プラットフォームに跨る。
どちらも v0.2 の範囲外にし、GitLab ルールはすべてオフラインで完結させる。

Forgejo は `uses: actions/checkout@v4` を既定で `code.forgejo.org` に解決するので、
GitHub API の答えは別物になる。Forgejo のファイルではネットワークルールを
`--quick` 相当で黙らせる（ロードマップ §4.1）。

### D7. 解決できない `include` / `extends` があるジョブでは「無い」ことを報告しない

GitLab の有効なジョブ定義は `default:` → `include` → `extends` → ジョブ本体のマージで
決まる。ローカル `include:` と `extends:` はオフラインで解決するが、`project:` /
`remote:` / `template:` / `component:` は解決できない。解決できない include を持つ
パイプラインでは「`image` が無い」「`timeout` が無い」のような欠落系のルールは黙る。
存在するものへの指摘（未固定のイメージ、汚染変数の展開）は出す。

### D8. v0.2 の対象は Gitea / Forgejo 方言と GitLab CI に限る

Gitea / Forgejo は差分が最小で、D1 / D3 の抽象を小さな変更で検証できる。GitLab は
GitHub に次ぐ利用規模でオフラインのセキュリティリンターが存在せず、D2 の
「独立 IR」を本当に必要とする最初のプラットフォームでもある。

Bitbucket Pipelines / Azure Pipelines / CircleCI / Buildkite は v0.3 以降の候補とし、
順序は v0.2 のリリース後に決める。Jenkins（Groovy DSL）は YAML ではないため、
ゼロ依存・自前 YAML パーサの方針と両立せず、対象外とする。Tekton / Argo Workflows は
Kubernetes CRD であり CI 設定の性質が違うので同じく対象外。

## Consequences

- `src/main.zig` の `documentLintFn` による「パス → 検査関数」の分岐が
  `Platform` へ一般化される。dependabot / action metadata の既存分岐はそのまま
  `github` の下に収まる
- 既定のファイル発見に `.gitlab-ci.yml` と `.gitea/` / `.forgejo/` が加わる。これまで
  緑だった CI が v0.2 で赤になり得るので、CHANGELOG の **Changed** に明記し、
  `ignore:` パターンで除外できることを README に書く
- ルール数は 98 → 110 前後になる。`docs/rules.md` はプラットフォームごとの節に分かれ、
  同期テストが接頭辞付き ID を数える
- YAML 層に GitLab の `!reference` タグ対応が入る（現在は `!reference [...]` を
  プレーンスカラーとして読み飛ばしている）。`Node` にタグを持たせる変更は fuzz
  コーパスにも及ぶ
- Gitea / Forgejo の `permissions:` / `concurrency:` のように版で対応が違う項目は、
  確認できるまで GitHub と同じ挙動のまま出す。扱いはロードマップ §4.1 の方言表
  1 箇所で管理する
