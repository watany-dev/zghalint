# v0.2 ロードマップ: GitHub Actions 以外の CI 対応

最終更新: 2026-09-08
判断の単一情報源は `docs/adr/0014-v0.2-multi-ci-platform.md`。本書はマイルストーン、
プラットフォームごとの差分、ルール案、テスト方針を記述する。

## 1. ゴール

v0.2.0 のリリース時点で次が成り立つこと。

1. `zghalint`（引数なし）が `.github/` / `.gitea/` / `.forgejo/` / `.gitlab-ci.yml` を
   1 回の実行で検査し、既存の CLI 契約（フラグ、終了コード、terminal / JSON / SARIF）が
   そのまま使える
2. Gitea / Forgejo Actions のワークフローに対し、方言差による偽陽性が出ない
3. GitLab CI に対し、セキュリティ・スキーマ・ベストプラクティスの中核ルール
   （§5 の "must"）がオフラインで動き、`docs/rules.md` に文書化され、bench で
   checkov と比較されている
4. 上記を GitHub Actions の既存 90 ルールの精度を落とさずに実現している
   （bench の GitHub ケースの採点が v0.1 と一致）

前提: v0.1 は現在のスコープ（GitHub Actions）で CLI 契約を固めたリリースとする。
v0.2 の作業は v0.1 のタグ後に始めるが、§6 の M0（tidying）は v0.1.x のうちに
入れてよい。挙動を変えないからである。

## 3. プラットフォーム調査と優先順位

### 3.1 注入モデルの違い

「untrusted な値がスクリプトに入る」ルール（GitHub の SEC002）は、プラットフォームの
展開モデルで意味が変わる。これが優先順位とルール設計の軸になる。

| プラットフォーム | 展開 | 意味 |
| --- | --- | --- |
| GitHub Actions `${{ }}` | テンプレート時（シェルがパースする前に文字列が埋め込まれる） | クォートしても防げない。**注入 = error** |
| Gitea / Forgejo `${{ }}` | 同上 | 同上。汚染源の表も同じ（`gitea.event.*` は `github.event.*` の別名） |
| Azure Pipelines `$(Build.SourceVersionMessage)` / `${{ }}` | テンプレート時 | GitHub と同型。error 相当 |
| CircleCI `<< pipeline.git.branch >>` | テンプレート時 | 同型 |
| GitLab CI `$CI_COMMIT_MESSAGE` | シェル実行時（環境変数として export され、シェルが展開する） | `"$VAR"` とクォートすれば注入にならない。危険なのは `eval`、クォート無しのコマンド置換、別インタプリタへの埋め込み。**シェル衛生 = warning** |
| Bitbucket Pipelines `$BITBUCKET_BRANCH` | シェル実行時 | 同上 |
| Buildkite `$BUILDKITE_MESSAGE` | シェル実行時 | 同上 |

GitLab には GitLab 側が展開するフィールドもある（`image:` / `services:` / `cache:key` /
`artifacts:name` / `environment:` / `rules:if` / `variables:` の値）。`image: my/$CI_COMMIT_REF_NAME`
のようにブランチ名がイメージ名を決める形は、コード実行ではなくサプライチェーンの
迂回になる。これは GL-SEC001 とは別に扱う（§5 の GL-SEC006 候補）。

### 3.2 候補と v0.2 での扱い

| プラットフォーム | 設定ファイル | 既存のオフラインリンター | 注入モデル | v0.2 |
| --- | --- | --- | --- | --- |
| Gitea / Forgejo Actions | `.gitea/workflows/`、`.forgejo/workflows/` | なし（actionlint は方言を知らない） | テンプレート時 | **対象**（方言） |
| GitLab CI | `.gitlab-ci.yml`、`include: local:` の断片 | `glab ci lint` はサーバ側検証。セキュリティ観点は checkov / KICS の数ルールのみ | シェル実行時 | **対象**（独立 IR） |
| Bitbucket Pipelines | `bitbucket-pipelines.yml` | checkov の数ルール | シェル実行時 | v0.3 候補 |
| Azure Pipelines | `azure-pipelines.yml`、テンプレート | checkov の数ルール | テンプレート時 | v0.3 候補 |
| CircleCI | `.circleci/config.yml` | `circleci config validate` はサーバ側 | テンプレート時 | v0.3 候補 |
| Buildkite | `.buildkite/pipeline.yml` | なし | シェル実行時 | v0.3 候補 |
| Jenkins | `Jenkinsfile`（Groovy） | — | — | 対象外（YAML でない） |
| Tekton / Argo Workflows | Kubernetes CRD | — | — | 対象外 |
| Travis CI | `.travis.yml` | — | — | 対象外（需要が細い） |

v0.3 候補の順序は v0.2 のリリース後に決める。判断材料は (1) 注入モデルが
テンプレート時であること（error 級の unique-win が作れる。Azure / CircleCI が該当）、
(2) issue の要望と reaction、(3) bench 用のコーパスが集められること。

## 4. 方言と YAML 層の差分

### 4.1 Gitea / Forgejo 方言表

`Workflow.dialect` を見る箇所。「保留」は実装時に公式ドキュメントで確認する項目で、
確認できるまでは GitHub と同じ挙動のまま出す（ADR Consequences）。

| 項目 | 差分 | 対応 |
| --- | --- | --- |
| ファイル発見 | `.gitea/workflows/`、`.forgejo/workflows/` | `collectDefaultFiles` に追加 |
| 式コンテキスト | `gitea.*` / `forgejo.*` は `github.*` の別名 | `expr_catalog.zig` に方言でのみ有効な別名を追加。SEC002 / SEC006 / SEC008 の汚染源表は `github.` 接頭辞を別名にも照合する |
| ランナーラベル | ラベルは `act_runner` の設定で決まり、`ubuntu-latest` も運用者の割当 | RUNNER001 / RUNNER002 / RUNNER003 を黙らせる（`runner.labels` が設定されていれば RUNNER002 は従う）。self-hosted と同じ扱い |
| `uses:` の解決先 | Gitea: 既定 `github.com`。Forgejo: 既定 `code.forgejo.org` | Forgejo 方言では SC004 / SC005 / SC008 を `--quick` 相当で省略（ADR D6）。SC002 / SC003 / SC007 はオフラインデータなので `owner/repo` 名が同じ限り出す |
| `uses:` の絶対 URL 形 | `uses: https://gitea.com/actions/checkout@v4` が有効 | `ActionRef.parse` が `https://<host>/owner/repo@ref` を受理し、DEP003 は方言下で拒否しない。`host` フィールドを追加 |
| `permissions:` | 版により未対応 / 部分対応 | 保留。確認後、未対応の版が主流なら SEC004 / SEC007 / PERM* を方言で黙らせる |
| `concurrency:` | 版により未対応 | 保留。BP005 は当面そのまま |
| Dependabot | Gitea / Forgejo は Renovate が主流 | 変更なし（DEP001 / DEP002 は `dependabot.yml` にしか出ない） |
| イベント | GitHub の部分集合 | 変更なし。SYN009 の表は GitHub の超集合なので偽陽性は出ない。方言で未対応のイベントを警告するルールは v0.2 では作らない |

### 4.2 YAML 層: `!reference` タグ

GitLab は `!reference [.job, key]` で他ジョブの配列を差し込む。トークナイザは
`!` で始まる語をタグとして切り出し、`Node` にタグ名（`?[]const u8`）を持たせる。
パーサは `!reference` の直後のフローシーケンスを通常どおり読み、タグ付きノードとして
返す。解決（差し込み）は YAML 層ではなく `src/gitlab/parser.zig` で行う。他のタグ
（`!!str` 等）は名前だけ保持して値は素通しにする。

fuzz コーパス（`src/fuzz_test.zig`）にタグ付きの種を足し、タグの終端がバッファを
越えないことを既存の「never leaves the source buffer」に含める。

## 5. GitLab CI のルール案

ID は ADR D4 の `GL-<CAT><NNN>`。"must" は v0.2.0 に入れるもの、"should" は
v0.2.x で追う候補。severity は GitHub 側の同趣旨ルールに揃えつつ、注入モデル
（§3.1）の違いを反映する。

### 5.1 スキーマ / 構文（GL-SYN）

| ID | name | severity | 内容 | 優先 |
| --- | --- | --- | --- | --- |
| GL-SYN001 | unknown-key | error | トップレベル / ジョブに GitLab のスキーマにないキー。キー表は GitLab が公開する `ci.json` JSON schema から生成し、`src/gitlab/schema.zig` に置く（GitHub の `schema.zig` と同じ形） | must |
| GL-SYN002 | undefined-stage | error | `stage:` が `stages:` に無い。`stages:` 省略時の既定は `.pre, build, test, deploy, .post` | must |
| GL-SYN003 | undefined-job-reference | error | `needs:` / `dependencies:` が存在しないジョブを指す。`needs: - project:`（別プロジェクト）と `optional: true` は対象外 | must |
| GL-SYN004 | undefined-extends | error | `extends:` の参照先が無い | must |
| GL-SYN005 | invalid-job | error | `script` / `trigger` / `run` のいずれも無いジョブ、予約語（`image` / `services` / `stages` / `types` / `before_script` / `after_script` / `variables` / `cache` / `include` / `true` / `false` / `nil`）をジョブ名にしたもの | must |
| GL-SYN006 | only-except-with-rules | error | 同じジョブで `only` / `except` と `rules` を併用（GitLab はパイプライン作成時に拒否する） | must |
| GL-SYN007 | needs-cycle | error | `needs:` の循環。#281（GitHub 側 G10）と同じアルゴリズムを `src/common/` に置いて共有 | should |
| GL-SYN008 | invalid-rules-if | error | `rules: - if:` の式（`$VAR == "x"`、`=~ /re/`、`&&` / `\|\|`、括弧、`null`）の構文エラー | should |

### 5.2 セキュリティ（GL-SEC）

| ID | name | severity | 内容 | 優先 |
| --- | --- | --- | --- | --- |
| GL-SEC001 | untrusted-variable-in-shell | warning | MR / commit 作者が値を決める定義済み変数（`CI_MERGE_REQUEST_TITLE` / `_DESCRIPTION` / `_SOURCE_BRANCH_NAME` / `_LABELS`、`CI_COMMIT_MESSAGE` / `_TITLE` / `_DESCRIPTION` / `_AUTHOR` / `_REF_NAME` / `_BRANCH` / `_TAG` / `_TAG_MESSAGE`）が `script` / `before_script` / `after_script` で **クォート無し**、`eval`、`sh -c "..."` の内側、`curl -d` 等の別インタプリタ引数に現れる。`"$CI_COMMIT_MESSAGE"` とクォートされた単独参照は報告しない（§3.1） | must |
| GL-SEC002 | hardcoded-secret | error | `variables:`（グローバル / ジョブ）の値が秘密情報に見える。`src/common/` の秘密情報ヒューリスティックを共有。修正案は masked / protected な CI/CD 変数 | must |
| GL-SEC003 | unpinned-include | warning | `include: remote:`（コミットで固定できない）、`include: project:` で `ref:` が無い（既定ブランチの HEAD に追随）、`include: component:` の版が `~latest` かブランチ名。`template:` と `local:` は対象外 | must |
| GL-SEC004 | unpinned-image | warning / info | `image:` / `services:` にタグが無い、または `latest`（warning）。タグはあるが digest が無い（info）。`default:` と `extends:` のマージ後の値で判定 | must |
| GL-SEC005 | remote-script-execution | warning | `script` 内の `curl ... \| sh` / `wget -O- ... \| bash`。`containsCurlWgetPipeShell` を共有 | must |
| GL-SEC006 | untrusted-variable-in-image | warning | `image:` / `services:` / `include:` に §5.2 GL-SEC001 の汚染変数が展開される（ブランチ名でイメージが決まる） | should |
| GL-SEC007 | unprotected-deployment | warning | `environment:` を持つジョブが `rules:` で protected な ref（`$CI_COMMIT_REF_PROTECTED == "true"` 等）に絞られていない | should |

GitLab 側で「fork の MR パイプラインを親プロジェクトで実行する」設定は YAML に
現れないため、GitHub の SEC005（`pull_request_target`）に相当するルールは作れない。
`docs/rules.md` の非スコープに書く。

### 5.3 ベストプラクティス（GL-BP）

| ID | name | severity | 内容 | 優先 |
| --- | --- | --- | --- | --- |
| GL-BP001 | missing-timeout | info | ジョブに `timeout:` が無く `default: timeout:` も無い。プロジェクト設定の既定（60 分）があるので GitHub の BP001（warning）より軽い | must |
| GL-BP002 | deprecated-only-except | info | `only` / `except` の使用。`rules:` へ移行 | must |
| GL-BP003 | missing-interruptible | info | MR パイプラインで動くジョブに `interruptible: true` が無い | must |
| GL-BP004 | artifacts-without-expire-in | info | `artifacts:` に `expire_in:` が無い | must |
| GL-BP005 | cache-without-key | warning | `cache:` に `key:` が無い（既定キー `default` を全ブランチで共有し、汚染と取り違えの原因になる） | must |
| GL-BP006 | missing-job-name-convention | — | GitHub の BP002（step の name）に相当するものは GitLab には無い。作らない | — |

### 5.4 パフォーマンス / 依存（GL-PERF, GL-DEP）

| ID | name | severity | 内容 | 優先 |
| --- | --- | --- | --- | --- |
| GL-PERF001 | missing-cache | info | `script` に `npm ci` / `pip install` / `go build` 等があり lockfile が存在するのに `cache:` が無い。`workspace.zig` の lockfile 検出を共有 | must |
| GL-DEP001 | include-local-missing | error | `include: local:`（および `include: - 'path.yml'` の短縮形）の参照先がリポジトリに無い。DEP004 / `local_action.zig` と同じくワークスペースルートから解決 | must |

### 5.5 autofix

v0.2.0 で `--fix` / `--fix-unsafe` を付けるもの:

| ルール | fix | safety |
| --- | --- | --- |
| GL-BP004 | `expire_in: 1 week` を挿入 | unsafe（保持期間を変える） |
| GL-BP003 | `interruptible: true` を挿入 | unsafe |
| GL-BP002 | `only` / `except` → `rules:` 変換 | 対象外（意味の対応が一対一でない） |
| GL-SEC004 | digest 固定 | 対象外（Docker Hub への問い合わせが要る。ADR D6） |

挿入は `fix/builder.zig` の `insertMappingEntryBlock` を使う。dependabot の
cooldown 挿入と同じ形なので新規の部品は要らない。

## 6. マイルストーン

各マイルストーンは複数の PR に分かれる。完了条件を満たすまで次へ進まない。

### M0. Tidying（挙動を変えない）

- `engine.Rule` から `RuleMeta` を分離し、SARIF と `docs_sync_test` が `[]const RuleMeta` を受ける
- `src/common/` を作り、ADR D5 の表の部品を移す（1 部品 1 コミット）
- `src/platform.zig`（`Platform` enum、`detectPlatform`）を追加し、`main.zig` の
  `documentLintFn` / `collectDefaultFiles` を `Platform` 経由に書き換える。この時点では
  `github` しか無い
- `docs_sync_test.zig` の `ruleRowId` と `config.zig` の ID 照合が `GL-SEC001` 形を通す
- `docs/rules.md` の見出しを「GitHub Actions」の下にまとめ直す準備（節の追加は M3）

完了条件: `python3 scripts/bench.py --json` の出力が M0 前後で一致。全 CI チェック緑。

### M1. Gitea / Forgejo 方言

- `.gitea/workflows/` / `.forgejo/workflows/` の発見、`Workflow.dialect`
- §4.1 の「対応」欄のうち保留でないものを実装
- `ActionRef` の絶対 URL 形と `host`
- `tests/fixtures/e2e-gitea/`（`gitea.*` コンテキストで EXPR002 が出ないこと、
  RUNNER* が出ないこと、Forgejo で SC004 系が出ないことを `forbid` で固定）
- `docs/rules.md` に「Gitea / Forgejo dialect」節。保留項目は表に「未確認」と書く

完了条件: Gitea / Forgejo の公開リポジトリから集めた 20 ファイル程度のコーパスで、
方言に起因する指摘が 0 件。

### M2. GitLab CI の IR とパーサ

- YAML 層: `!reference` タグ（§4.2）
- `src/gitlab/types.zig`: `Pipeline`（`stages` / `default` / `variables` / `include` /
  `workflow`）、`Job`（キーワードごとの値と span）、隠しジョブ（`.name`）
- `src/gitlab/parser.zig`: `default:` → `include: local:` → `extends:` → ジョブ本体の
  マージ。マージ規則（マッピングは深いマージ、配列は置換、`!reference` は差し込み）は
  GitLab の文書に従い、設計書 `docs/design/gitlab-parser-design.md` に表で残す
- `src/gitlab/schema.zig`: `ci.json` から生成したキー表と生成スクリプト
  （`scripts/gen-gitlab-schema.py`。生成物はコミットし、CI で再生成差分が無いことを確認）
- `include: local:` の断片ファイルを単独で渡されたときは「断片モード」で読み、
  `stages` の欠落などルート前提のルールを黙らせる
- ルールエンジン: `src/rules/gitlab/engine.zig`（`Rule` with `check_pipeline` /
  `check_job`）と `registry.zig`。`registry.documented_rule_ids` へ連結

完了条件: GitLab 公式のサンプルと公開リポジトリから集めた 50 ファイル程度を
パースエラーなしで読める。PBT の `test_crash` / `test_determinism` を GitLab の
生成器で通す。

## 7. テスト方針

| 種類 | 内容 |
| --- | --- |
| インライン単体 | 各ルール・パーサ関数。既存と同じ |
| E2E | `tests/fixtures/e2e-gitea/`、`tests/fixtures/e2e-gitlab/`。`# zghalint:expect` / `forbid` の記法はそのまま。`e2e_test.zig` はディレクトリごとにプラットフォームを決めて対応するパイプラインへ流す |
| docs 同期 | `documented_rule_ids` の和集合と `docs/rules.md` の突き合わせ。接頭辞付き ID を数える |
| PBT | `tests/pbt/strategies.py` に GitLab の生成器。`test_crash` / `test_determinism` / `test_output_consistency` / `test_autofix_idempotency` は生成器を差し替えるだけで流用できる。`test_security_detection` は GL-SEC001 用に「クォート無し参照を含む script は必ず報告される」を追加 |
| fuzz | YAML 層は共有なので既存ターゲットで足りる。`!reference` の種を追加。GitLab パーサ用のターゲットを 1 本追加 |
| bench | checkov（GitLab / 以後 Bitbucket / Azure / CircleCI も同じアダプタ）。actionlint / zizmor は GitHub ケースのまま |
| 形式手法 | M4 で GL-SEC001 の表を Z3 に載せる |

## 8. リスク

| リスク | 影響 | 手当て |
| --- | --- | --- |
| GitLab の `extends` / `include` マージ規則の再現漏れ | 有効なジョブ定義を取り違え、欠落系ルールが偽陽性を出す | ADR D7（解決できないものがあれば黙る）。マージ規則を表にして PBT で「マージ順序を入れ替えても結果が変わらない」性質を検証 |
| GL-SEC001 のクォート判定の甘さ | 注入モデルの違いを反映できず、GitHub の SEC002 と同じ勢いで出すと偽陽性の山になる | severity を warning に固定。単独のクォート済み参照は必ず黙る。判定表を `docs/rules.md` に明記し、bench の j-clean 相当（GitLab 版）で 0 件を固定 |
| YAML 層のタグ対応が既存の GitHub 解析を壊す | 90 ルールの回帰 | fuzz コーパスの拡張と bench の一致確認を M2 の完了条件に含める |
| Gitea / Forgejo の `permissions:` 対応状況が版で違う | 黙らせると本当に必要な指摘を落とし、出すと偽陽性 | 保留項目は「確認できるまで GitHub と同じ」。方言表を版付きで記録する |
| 既定のファイル発見の拡張で利用者の CI が赤になる | v0.2 への更新が躊躇される | CHANGELOG **Changed** に明記。`ignore:` と `platform:` で戻せることを README に書く |
| ルール数の倍増で `docs/rules.md` が読みにくくなる | 利用者がルールを探せない | プラットフォームごとに節を分け、先頭にプラットフォーム別の索引表を置く |

## 9. 決めていないこと

- v0.3 の対象プラットフォームの順序（§3.2 の判断材料で v0.2 リリース後に決める）
- `src/workflow/` を `src/github/` に付け替えるか（v0.2 完了後の tidying として判断）
- Docker Hub の tag → digest 解決を持つか（GL-SEC004 の autofix と GitHub の SEC013 系
  の両方に効くが、ネットワーク層の第 2 のホストになる。v0.3 以降）
