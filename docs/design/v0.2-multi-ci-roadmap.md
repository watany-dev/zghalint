# v0.2 ロードマップ: GitHub Actions 以外の CI 対応

最終更新: 2026-09-08
判断の単一情報源は `docs/adr/0014-v0.2-multi-ci-platform.md`。本書はマイルストーン、
プラットフォームごとの差分、ルール案、テスト方針を記述する。

## 1. ゴール

v0.2.0 のリリース時点で次が成り立つこと。

1. `zghalint`（引数なし）が `.github/` / `.gitea/` / `.forgejo/` / `.gitlab-ci.yml` を
   1 回の実行で検査し、既存の CLI 契約（フラグ、終了コード、terminal / JSON / SARIF）が
   そのまま使える
2. Gitea / Forgejo Actions のワークフローに対し、方言差による偽陽性が出ない
3. GitLab CI に対し、セキュリティ・スキーマ・ベストプラクティスの中核ルール
   （§5）がオフラインで動き、`docs/rules.md` に文書化され、bench で
   checkov と比較されている
4. 上記を GitHub Actions の既存ルールの精度を落とさずに実現している
   （bench の GitHub ケースの採点が v0.1 と一致）

前提: v0.1 は現在のスコープ（GitHub Actions）で CLI 契約を固めたリリースとする。
v0.2 の作業は v0.1 のタグ後に始めるが、§6 の M0（tidying）は v0.1.x のうちに
入れてよい。挙動を変えないからである。

## 2. 現状の依存関係の棚卸し

CI に依存しているのは次の 5 箇所で、他（`src/yaml/`、`src/diagnostics.zig`、
`src/output/`、`src/config.zig`、`src/fix/`、`src/workspace.zig`）は無変更で共有する。

- `src/workflow/` と `src/rules/*.zig`: GitHub Actions の IR / スキーマ / 型。
  GitHub 専用のまま残し、汎用部品だけ `src/common/` へ（ADR D5）
- `src/rules/{prefetch,graphql,rest_fallback,disk_cache}.zig`: GitHub API。
  GitHub 専用のまま（ADR D6）
- `src/main.zig`: `.github/` 前提のファイル発見と `documentLintFn` の分岐。
  `Platform` へ一般化
- `src/docs_sync_test.zig`: `ruleRowId` が `[A-Z]+[0-9]+` しか読まない。接頭辞付き
  ID を受理。SARIF は `registry.all_rules` を descriptor に使うので `RuleMeta` の
  和集合を渡す
- フィクスチャ: `tests/fixtures/e2e/`、`bench/cases/`、`tests/pbt/` の生成器は
  GitHub 前提。プラットフォームごとに追加

現状の実バイナリで確認した事実:

- `.gitlab-ci.yml` を渡すと `workflow parse error: MissingField: 'on'` で終了コード 2
- `${{ gitea.ref }}` は `EXPR002 unknown context: 'gitea'` になる
- `!reference [.job, script]` は YAML エラーにならず、プレーンスカラーとして
  読み飛ばされる（タグを字句として認識していない）

## 3. 注入モデルの違い

「untrusted な値がスクリプトに入る」ルール（GitHub の SEC002）は、プラットフォームの
展開モデルで意味が変わる。GitHub / Gitea / Forgejo の `${{ }}` はシェルがパースする
前に文字列を埋め込むので、クォートしても防げず **注入 = error** である。GitLab の
`$CI_COMMIT_MESSAGE` は環境変数としてシェルが展開するので、`"$VAR"` とクォート
すれば注入にならず、危険なのは `eval`、クォート無しのコマンド置換、別インタプリタ
への埋め込みに限られる。**シェル衛生 = warning** として扱う（GL-SEC001）。

GitLab には GitLab 側が展開するフィールドもある（`image:` / `services:` / `cache:key` /
`artifacts:name` / `environment:` / `rules:if` / `variables:` の値）。`image: my/$CI_COMMIT_REF_NAME`
のようにブランチ名がイメージ名を決める形は、コード実行ではなくサプライチェーンの
迂回になる。これは GL-SEC001 とは別に扱う（§9 の GL-SEC006 候補）。

v0.2 の対象は Gitea / Forgejo（方言）と GitLab CI（独立 IR）の 2 つ。対象外と
v0.3 候補は ADR D8 にある。

## 4. 方言と YAML 層の差分

### 4.1 Gitea / Forgejo 方言表

`Workflow.platform` を見る箇所。「保留」は実装時に公式ドキュメントで確認する項目で、
確認できるまでは GitHub と同じ挙動のまま出す（ADR Consequences）。

| 項目 | 差分 | 対応 |
| --- | --- | --- |
| 式コンテキスト | `gitea.*` は `github.*` の別名（`forgejo.*` の存在は未確認。M1 で forgejo-runner の実装を見て決める） | `expr_catalog.zig` に方言でのみ有効な別名を追加。SEC002 / SEC006 / SEC008 の汚染源表は `github.` 接頭辞を別名にも照合する |
| ランナーラベル | ラベルは `act_runner` の設定で決まり、`ubuntu-latest` も運用者の割当 | RUNNER001 / RUNNER002 / RUNNER003 を黙らせる（`runner.labels` が設定されていれば RUNNER002 は従う）。self-hosted と同じ扱い |
| `uses:` の解決先 | Gitea: 既定 `github.com`。Forgejo: 既定 `code.forgejo.org` | Forgejo では SC003–SC006 / SC008 を `--quick` 相当で省略（ADR D6）。SC001 / SC002 はオフラインなのでそのまま出す |
| `uses:` の絶対 URL 形 | `uses: https://gitea.com/actions/checkout@v4` が有効 | `ActionRef.parse`（`src/workflow/types.zig`）が `https://<host>/` を受理して読み捨て、DEP003 は方言下で拒否しない。読む側がいないので `host` は保持しない |
| `permissions:` | 版により未対応 / 部分対応 | 保留。確認後、未対応の版が主流なら SEC004 / SEC007 / PERM* を方言で黙らせる |
| `concurrency:` | 版により未対応 | 保留。BP005 は当面そのまま |

Dependabot（Renovate が主流）とイベント表（GitHub の部分集合）は差分があっても
偽陽性を生まないので手を入れない。

### 4.2 YAML 層: `!reference` タグ

GitLab は `!reference [.job, key]` で他ジョブの配列を差し込む。トークナイザは
`!` で始まる語をタグとして切り出し、`Node` にタグ名（`?[]const u8`）を持たせる。
パーサは `!reference` の直後のフローシーケンスを通常どおり読み、タグ付きノードとして
返す。解決（差し込み）は YAML 層ではなく `src/gitlab/parser.zig` で行う。他のタグ
（`!!str` 等）は名前だけ保持して値は素通しにする。

fuzz コーパス（`src/fuzz_test.zig`）にタグ付きの種を足し、タグの終端がバッファを
越えないことを既存の「never leaves the source buffer」に含める。

## 5. GitLab CI のルール案

ID は ADR D4 の `GL-<CAT><NNN>`。ここに挙げるものはすべて v0.2.0 に入れる。
severity は GitHub 側の同趣旨ルールに揃えつつ、注入モデル（§3）の違いを反映する。
v0.2.x に回す候補は §9。

### 5.1 スキーマ / 構文（GL-SYN）

| ID | name | severity | 内容 |
| --- | --- | --- | --- |
| GL-SYN001 | unknown-key | error | トップレベル / ジョブに GitLab のスキーマにないキー。キー表は GitLab が公開する `ci.json` JSON schema を読んで `src/gitlab/schema.zig` に手書きする（GitHub の `schema.zig` と同じ形） |
| GL-SYN002 | undefined-stage | error | `stage:` が `stages:` に無い。`stages:` 省略時の既定は `.pre, build, test, deploy, .post` |
| GL-SYN003 | undefined-job-reference | error | `needs:` / `dependencies:` が存在しないジョブを指す。`needs: - project:`（別プロジェクト）と `optional: true` は対象外 |
| GL-SYN004 | undefined-extends | error | `extends:` の参照先が無い |
| GL-SYN005 | invalid-job | error | `script` / `trigger` / `run` のいずれも無いジョブ、予約語（`image` / `services` / `stages` / `types` / `before_script` / `after_script` / `variables` / `cache` / `include` / `true` / `false` / `nil`）をジョブ名にしたもの |
| GL-SYN006 | only-except-with-rules | error | 同じジョブで `only` / `except` と `rules` を併用（GitLab はパイプライン作成時に拒否する） |

### 5.2 セキュリティ（GL-SEC）

| ID | name | severity | 内容 |
| --- | --- | --- | --- |
| GL-SEC001 | untrusted-variable-in-shell | warning | MR / commit 作者が値を決める定義済み変数（`CI_MERGE_REQUEST_TITLE` / `_DESCRIPTION` / `_SOURCE_BRANCH_NAME` / `_LABELS`、`CI_COMMIT_MESSAGE` / `_TITLE` / `_DESCRIPTION` / `_AUTHOR` / `_REF_NAME` / `_BRANCH` / `_TAG` / `_TAG_MESSAGE`）が `script` / `before_script` / `after_script` で **クォート無し**、`eval`、`sh -c "..."` の内側、`curl -d` 等の別インタプリタ引数に現れる。`"$CI_COMMIT_MESSAGE"` とクォートされた単独参照は報告しない（§3） |
| GL-SEC002 | hardcoded-secret | error | `variables:`（グローバル / ジョブ）の値が秘密情報に見える。`src/common/` の秘密情報ヒューリスティックを共有。修正案は masked / protected な CI/CD 変数 |
| GL-SEC003 | unpinned-include | warning | `include: remote:`（コミットで固定できない）、`include: project:` で `ref:` が無い（既定ブランチの HEAD に追随）、`include: component:` の版が `~latest` かブランチ名。`template:` と `local:` は対象外 |
| GL-SEC004 | unpinned-image | warning / info | `image:` / `services:` にタグが無い、または `latest`（warning）。タグはあるが digest が無い（info）。`default:` と `extends:` のマージ後の値で判定 |
| GL-SEC005 | remote-script-execution | warning | `script` 内の `curl ... \| sh` / `wget -O- ... \| bash`。`containsCurlWgetPipeShell` を共有 |

GitLab 側で「fork の MR パイプラインを親プロジェクトで実行する」設定は YAML に
現れないため、GitHub の SEC005（`pull_request_target`）に相当するルールは作れない。
`docs/rules.md` の GL 節の冒頭に書く。

### 5.3 ベストプラクティス（GL-BP）

| ID | name | severity | 内容 |
| --- | --- | --- | --- |
| GL-BP001 | missing-timeout | info | ジョブに `timeout:` が無く `default: timeout:` も無い。プロジェクト設定の既定（60 分）があるので GitHub の BP001（warning）より軽い |
| GL-BP002 | deprecated-only-except | info | `only` / `except` の使用。`rules:` へ移行 |
| GL-BP003 | missing-interruptible | info | MR パイプラインで動くジョブに `interruptible: true` が無い |
| GL-BP004 | artifacts-without-expire-in | info | `artifacts:` に `expire_in:` が無い |
| GL-BP005 | cache-without-key | warning | `cache:` に `key:` が無い（既定キー `default` を全ブランチで共有し、汚染と取り違えの原因になる） |

### 5.4 パフォーマンス / 依存（GL-PERF, GL-DEP）

| ID | name | severity | 内容 |
| --- | --- | --- | --- |
| GL-PERF001 | missing-cache | info | `script` に `npm ci` / `pip install` / `go build` 等があり lockfile が存在するのに `cache:` が無い。`workspace.zig` の lockfile 検出を共有 |
| GL-DEP001 | include-local-missing | error | `include: local:`（および `include: - 'path.yml'` の短縮形）の参照先がリポジトリに無い。DEP004 / `local_action.zig` と同じくワークスペースルートから解決 |

### 5.5 autofix

| ルール | fix | safety |
| --- | --- | --- |
| GL-BP004 | `expire_in: 1 week` を挿入 | unsafe（保持期間を変える） |
| GL-BP003 | `interruptible: true` を挿入 | unsafe |

どちらもスカラー 1 行の挿入なので、BP001 の `timeout-minutes` と同じ
`fix/builder.zig` の `insertMappingEntry` を使う。新規の部品は要らない。

## 6. マイルストーン

各マイルストーンは複数の PR に分かれる。完了条件を満たすまで次へ進まない。

- `engine.Rule` から `RuleMeta` を分離し、SARIF と `docs_sync_test` が `[]const RuleMeta` を受ける

- `src/platform.zig`（`Platform` enum、`detectPlatform`）を追加し、`main.zig` の
  `documentLintFn` / `collectDefaultFiles` を `Platform` 経由に書き換える。この時点では
  `github` しか無い
- `docs_sync_test.zig` の `ruleRowId` が `GL-SEC001` 形を通す

完了条件: `python3 scripts/bench.py --json` の出力が M0 前後で一致。全 CI チェック緑。

### M1. Gitea / Forgejo 方言

- `.gitea/workflows/` / `.forgejo/workflows/` の発見、`Workflow.platform`、
  `--platform` と設定の `platform:`
- §4.1 の「対応」欄のうち保留でないものを実装
- `tests/fixtures/e2e-gitea/`（`gitea.*` コンテキストで EXPR002 が出ないこと、
  RUNNER* が出ないこと、Forgejo で SC004 系が出ないことを `forbid` で固定）
- `docs/rules.md` に「Gitea / Forgejo dialect」節。保留項目は表に「未確認」と書く

完了条件: Gitea / Forgejo の公開リポジトリから集めた 20 ファイル程度のコーパスで、
方言に起因する指摘が 0 件。

### M2. GitLab CI の IR とパーサ

- YAML 層: `!reference` タグ（§4.2）
- `src/gitlab/types.zig`: `Pipeline`（`stages` / `default` / `variables` / `include` /
  `workflow`）、`Job`（キーワードごとの値と span）、隠しジョブ（`.name`）
- `src/gitlab/parser.zig`: `default:` → `include: local:` → `extends:` → ジョブ本体の
  マージ。マージ規則（マッピングは深いマージ、配列は置換、`!reference` は差し込み）は
  GitLab の文書に従い、設計書 `docs/design/gitlab-parser-design.md` に表で残す
- `src/gitlab/schema.zig`: `ci.json` を読んで手書きしたキー表
- `include: local:` の断片ファイルはルートからの `include` 経由でだけ読む。単独で
  渡されたときは v0.2 では非対応（ルート前提のルールが偽陽性を出すため、
  `docs/rules.md` に書く）
- ルールエンジン: `src/rules/gitlab/engine.zig`（`Rule` with `check_pipeline` /
  `check_job`）と `registry.zig`。`registry.documented_rule_ids` へ連結

完了条件: GitLab 公式のサンプルと公開リポジトリから集めた 50 ファイル程度を
パースエラーなしで読める。PBT の `test_crash` / `test_determinism` を GitLab の
生成器で通す。

## 7. テスト方針

| 種類 | 内容 |
| --- | --- |
| E2E | `tests/fixtures/e2e-gitea/`、`tests/fixtures/e2e-gitlab/`。`# zghalint:expect` / `forbid` の記法はそのまま。`e2e_test.zig` はディレクトリごとにプラットフォームを決めて対応するパイプラインへ流す |
| docs 同期 | `documented_rule_ids` の和集合と `docs/rules.md` の突き合わせ。接頭辞付き ID を数える |
| PBT | `tests/pbt/strategies.py` に GitLab の生成器。`test_crash` / `test_determinism` / `test_output_consistency` / `test_autofix_idempotency` は生成器を差し替えるだけで流用できる。`test_security_detection` は GL-SEC001 用に「クォート無し参照を含む script は必ず報告される」を追加 |
| fuzz | YAML 層は共有なので既存ターゲットで足りる。`!reference` の種を追加。GitLab パーサ用のターゲットを 1 本追加 |
| bench | GitLab ケースは checkov。actionlint / zizmor は GitHub ケースのまま |

## 8. リスク

| リスク | 影響 | 手当て |
| --- | --- | --- |
| GitLab の `extends` / `include` マージ規則の再現漏れ | 有効なジョブ定義を取り違え、欠落系ルールが偽陽性を出す | ADR D7（解決できないものがあれば黙る）。マージ規則を表にして PBT で「マージ順序を入れ替えても結果が変わらない」性質を検証 |
| GL-SEC001 のクォート判定の甘さ | 注入モデルの違いを反映できず、GitHub の SEC002 と同じ勢いで出すと偽陽性の山になる | severity を warning に固定。単独のクォート済み参照は必ず黙る。判定表を `docs/rules.md` に明記し、bench の j-clean 相当（GitLab 版）で 0 件を固定 |
| YAML 層のタグ対応が既存の GitHub 解析を壊す | 既存ルールの回帰 | fuzz コーパスの拡張と bench の一致確認を M2 の完了条件に含める |

## 9. 決めていないこと

- v0.2.x の追加候補: GL-SYN007 needs-cycle（#281 の GitHub 側と同じアルゴリズムを
  `src/common/` で共有）、GL-SYN008 invalid-rules-if、GL-SEC006
  untrusted-variable-in-image（§3 の GitLab 側展開）、GL-SEC007 unprotected-deployment
  （`environment:` を持つジョブが protected な ref に絞られていない）
- v0.3 の対象プラットフォームの順序。判断材料は (1) 注入モデルがテンプレート時で
  error 級の unique-win が作れること、(2) issue の要望と reaction、(3) bench 用の
  コーパスが集められること
