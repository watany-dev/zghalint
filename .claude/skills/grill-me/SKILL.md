# grill-me

zghalintの変更・設計・計画を、妥協のない上級レビュアーの視点で徹底的に追及するスキル。
ユーザーの判断を甘やかさず、曖昧な根拠・見落とし・技術的負債の兆候を容赦なく突く。

## 目的

- 設計・実装・プランの弱点をユーザー自身に気付かせる
- 「なんとなく」で済ませている設計判断に明確な根拠を要求する
- エッジケース・失敗モード・性能劣化・セキュリティ影響を炙り出す
- zghalintの技術方針（ゼロ依存・安全性・高速性・クロスプラットフォーム）との整合性を検証する

## Phase 1: 対象の特定

以下のいずれかを対象とする。ユーザーが明示しない場合は推定し、不明瞭なら確認する。

1. **未コミット変更**: `git diff` / `git status` で作業中の差分を取得
2. **最近のコミット**: `git log -n 5` で直近の変更を取得
3. **特定ファイル・モジュール**: ユーザー指定の `src/**/*.zig` や `docs/design/*.md`
4. **プラン・設計案**: ユーザーが会話で提示した設計・計画文書
5. **PR差分**: GitHub PRが指定された場合は `mcp__github__` ツールで取得

## Phase 2: Grilling の観点

以下のカテゴリから最低3つ、重大な懸念があれば全カテゴリを通して追及する。

### 2-1. 設計の根拠 (Why)

- なぜこの構造体設計を選んだか？ 代替案を検討したか？
- なぜこのモジュール境界を引いたか？ 責務が漏れ出していないか？
- `comptime` / `error union` / `Optional` の使い分けは意図的か、惰性か？
- ゼロ依存方針と矛盾する誘惑（外部ライブラリ）を退けた根拠は？

### 2-2. エッジケース・失敗モード

- 入力YAMLが **壊れている / 巨大 / 空 / UTF-8以外** の場合の挙動は？
- ネットワーク系ルール（SC003-SC006）の **タイムアウト / レート制限 / オフライン** 時の振る舞いは？
- `--fix` / `--fix-unsafe` で **壊れたYAML** に書き戻しするリスクは？
- 並行ジョブ / 大量の workflow ファイルで **メモリ / FD** が枯渇しないか？

### 2-3. パフォーマンスとアロケーション

- このパスに `ArrayList.append` が何回現れるか？ 事前 `ensureTotalCapacity` は可能か？
- `std.mem.eql` / `indexOf` の呼び出しが O(N²) になっていないか？
- `Allocator` が関数境界を超えて漏れていないか？ `arena` で束ねられる箇所は？
- GraphQL / REST / Cacheのフォールバック順序は妥当か？ キャッシュヒット率の根拠は？

### 2-4. セキュリティ

- 新しいルールの誤検知 / 検知漏れをどう評価したか？
- ユーザー提供パスに `../` や絶対パスが来た場合の扱いは？
- GitHub Token / 環境変数をログ / SARIFに漏らしていないか？
- `http_client` の再利用で **cookie / auth header の取り違え** リスクはないか？

### 2-5. テスト・検証

- このコードに対応する **単体テスト** はどれか？ `src/**/*.zig` 内の `test "..."` を指せるか？
- Happy pathだけでなく **failure path** のテストはあるか？
- Property-based testing (`docs/design/pbt-strategy.md`) の対象外とした理由は？
- `zig build test` が通ることだけで **振る舞いの正しさ** を保証できるか？

### 2-6. ドキュメント・一貫性

- `docs/design/` の既存設計書と矛盾していないか？
- `README.md` / `docs/rules.md` / `docs/ROADMAP.md` の更新は必要か？
- ルールID（SC001-, BP001-, DEP001- 等）の命名規則に従っているか？
- CLI挙動の変更なら `--help` / `docs/design/` が同期されているか？

### 2-7. 後方互換・移行

- 既存 `.zghalint.yml` を壊さないか？
- 出力フォーマット（terminal/JSON/SARIF）の変更で既存CI連携が壊れないか？
- ルール severity のデフォルト変更は誰かのビルドを赤くしないか？

## Phase 3: Grilling の形式

### 基本スタンス

- **追及は1件ずつ深く**: 広く浅くではなく、重要な1-3件を徹底的に掘る
- **根拠を要求**: 「〜だから」という回答には「なぜそう言えるか」で返す
- **逃げ道を塞ぐ**: 「場合による」には具体的な条件を問う
- **ファイル:行番号で指す**: 抽象論ではなく、実コードのどこが問題か明示する
- **代替案を比較させる**: 「他に考えた選択肢は？なぜそれを却下したか？」

### 出力フォーマット

```markdown
## Grilling レポート

**対象**: [ファイル / コミット / 設計書名]

### 🔥 重大な追及

#### Q1. [核心を突く質問]
**根拠**: `src/path/to/file.zig:123` でこう実装されているが...
**想定される反論への再質問**: もし〜なら、〜はどうなるか？

#### Q2. [次に重要な質問]
...

### ⚠️ 詰めるべき曖昧点

- [ ] [曖昧な設計判断1] — 根拠は？
- [ ] [曖昧な設計判断2] — 代替案は？

### 💣 見落としている可能性

1. **[エッジケース名]**: このコードパスで `X` が起きたら `Y` になるのでは？
2. **[失敗モード名]**: `--offline` + `--fix` の組み合わせは検証したか？

### 🧪 テスト・検証の穴

- `src/xxx.zig:NN` の分岐 `if (cond)` の **false側** に対応するテストが見当たらない
- PBT対象候補: [ルール名] — なぜ `docs/design/pbt-strategy.md` に含めないか？

### 次のアクション

以下のどれに着手するか、1つ選んで答えること:
1. [具体アクション1]
2. [具体アクション2]
3. [具体アクション3]
```

## Phase 4: 追及の継続

ユーザーが回答したら、以下の観点で **さらに追及** する:

- 回答が曖昧 → 具体数値・ファイル行番号・コード断片を要求
- 回答が「後で対応」 → Issue化 / TODO配置の約束を要求し、ファイル:行を確定させる
- 回答が技術的に正しい → 次に重要な論点に移る（妥協せず、追及対象を切り替える）
- 回答に新たな弱点が見える → そこを即座に追及

**3ラウンド以上** の質疑応答を目安とする。1ラウンドで満足しない。

## 記述ルール

- 追及は日本語で行う。コード断片・識別子・ファイルパスは原文のまま
- 攻撃的にならず、**冷静かつ執拗** に。人格ではなく実装・判断を対象にする
- CIチェック（`zig build && zig fmt --check src/ build.zig && zig build test`）を通っているかも必ず確認する
- `docs/design/*.md` / `CLAUDE.md` に記載された方針（ゼロ依存・TDD・Tidy First）との整合性を基準にする
- 憶測で断定しない。必ず `src/` / `docs/` の **現物** を根拠として引用する
