# update-docs

ソースコードの現状に基づき、すべてのドキュメントを一括で最新化する Codex 用スキル。

## Phase 1: ソースコードの現状把握

1. `src/` 配下のZigソースコードを読み込む
   - `src/main.zig` - CLIエントリポイントと引数パース
   - `src/lib.zig` - ライブラリ公開APIとテストオーケストレーション
   - `src/config.zig` - 設定パース・ルールオーバーライド
   - `src/diagnostics.zig` - 診断型・重要度・カテゴリ
   - `src/rules/` - リントルール実装
   - `src/workflow/` - ワークフローデータ構造・パース
   - `src/yaml/` - YAMLパース（外部依存なし自前実装）
   - `src/output/` - 出力フォーマッタ
2. `build.zig` のビルド構成を確認する
3. `build.zig.zon` の依存パッケージ一覧を確認する
4. 公開API・構造体・enumの一覧を把握する

## Phase 2: 各ドキュメントの更新

### 2-1. 設計書 (`docs/design/<feature>.md`)

1. 各設計書の内容をソースコードと照合する
2. 以下を更新する:
   - モジュール構成の変更
   - 構造体・enumの追加・変更・削除
   - 関数シグネチャの変更
   - ビルドオプションの変更
3. 設計書が存在しない新機能がある場合、設計書の新規作成を提案する

### 2-2. README.md

1. プロジェクト概要が最新か確認する
2. インストール・ビルド手順を確認する
3. 使用方法・CLIオプションの説明を確認する
4. アーキテクチャ図・モジュール構成が最新か確認する

### 2-3. AGENTS.md

1. Codex 用の開発ガイドが最新か確認する
2. `README.md` と `CLAUDE.md` の内容と矛盾がないか確認する
3. 完了条件、ビルド手順、主要モジュール説明が実装と一致しているか確認する

## Phase 3: 一貫性チェック

すべてのドキュメント間で以下の一貫性を確認する:

1. **モジュール名・構造体名の統一**
2. **コマンド参照の統一**
3. **ファイルパス参照の統一**
4. **依存情報の統一**
5. **`@import` 文の検証**

## Phase 4: 更新レポートの出力

以下の形式で更新内容をレポートする:

```markdown
## ドキュメント更新レポート

### 更新したドキュメント
| ファイル | 更新内容 |
|---------|---------|
| docs/design/xxx.md | [変更概要] |
| README.md | [変更概要] |
| AGENTS.md | [変更概要] |

### 新規作成を提案するドキュメント
- [ファイル名]: [理由]

### 検出した不整合
- [不整合の詳細]
```

## 記述ルール

- コード例はZigで記述すること
- README.mdは英語で記述すること
- 開発ドキュメント（設計書・エージェント向け文書）は日本語または既存文書の言語に合わせること
- 構造体名・関数名はZigの命名規則（camelCase / PascalCase）に従うこと
- 定数名はscreaming_snake_caseまたはZigの慣例に従うこと
- Codex 用の参照は `AGENTS.md` と `.agents/skills/` を優先すること
